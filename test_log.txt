# Docker vs Kubernetes

## The short answer

| What it does | Docker | Kubernetes |
|--------------|-------|------------|
| Runs one container | Yes | No — runs *orchestrates* many containers |
| Gives you isolation at the filesystem level | Yes | No — gives you orchestration |
| Manages dependencies (ports, volumes) per container | Yes | No — per deployment |
| Answers: "what runs where" | No | Yes |

## The core distinction

Docker solves *one* problem: containerization — it packages your app + its dependencies into a single unit that moves consistently from dev to prod.

Kubernetes solves the next-order problem: running thousands of containers across dozens of machines. It answers questions like:

- Which pods should run on which nodes?
- How many replicas do I want?
- What happens when a node dies?
- How do I expose services externally?
- When should I drain nodes for maintenance?

## The actual overlap

You need both. You write Dockerfiles (or buildspecs, or manifests), you package images with Docker. You *deploy* those images into Kubernetes — not directly onto machines.

## The mental model

```
Docker: One container = one executable + one filesystem + one environment
Kubernetes: One deployment = zero downtime upgrades, service discovery, scaling, availability guarantees
```

The confusion comes when people think "Docker is orchestration" — it isn't. It's a file format. The orchestrator consumes Docker images.

        if answer is found:

| Работает | Нарушение |
